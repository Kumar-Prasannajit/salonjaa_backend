### Module 4 — Catalogue + Staff
- Migration `0003_clever_living_tribunal.sql` (staff, staff_leaves, branch_services, service_categories, staff_services)
- `POST/GET /api/v1/staff`, `GET/PATCH/DELETE /api/v1/staff/:id` — all require `SALON_OWNER` role + branch ownership (`BranchService.assertOwned`, now public for cross-module use — see Branch's Staff/Service note below). `GET /staff` takes optional `branchId` query; omitted lists staff across every branch the caller owns (same pattern as `GET /branches`'s optional `salonId`). `DELETE` soft-deletes (`deletedAt`).
- `POST /api/v1/staff/:id/leave`, `DELETE /api/v1/staff/:id/leave/:leaveId` — leave cancellation sets `status = CANCELLED` per TRD ("cancellation changes status, never removes record") — `staff_leaves` has no `deletedAt` column, this is intentional, not a missed soft-delete.
- `POST/GET /api/v1/services`, `GET/PATCH/DELETE /api/v1/services/:id` — same branch-ownership + optional-`branchId` pattern as Staff. Table is `branch_services` in the DB (TRD naming), exposed as `/services` per frontend_handover.md.
- `POST /api/v1/services/:id/staff`, `DELETE /api/v1/services/:id/staff/:staffId` — staff↔service assignment; 409 on duplicate assignment, 404 if the staff member isn't in the same branch as the service (existence not leaked across branches, same philosophy as `assertOwned`).
- **`service_categories` has no CRUD endpoint anywhere in the docs** (TRD calls it "platform category lifecycle"; the Admin API inventory is empty in frontend_handover.md). Rows come only from `npm run db:seed` (8 starter categories) — same precedent as `db:grant-role` for roles. Build a real Admin endpoint only when that module defines the contract; don't add owner-facing category CRUD speculatively.
- **Deferred (real TRD table, no documented endpoint):** `service_images` (multi-image gallery per service). `branch_services` does have a single `imageUrl` column (TRD's "image URL"), settable via `PATCH /services/:id` — same precedent as `salons.logo`/`coverImage` being PATCH-only, undocumented-in-create fields.
- Money/experience fields (`basePrice`, `salary`, `consultationFee`) use `doublePrecision`, not `numeric` — the installed `drizzle-orm@0.33` doesn't support `numeric(..., { mode: "number" })`, and this codebase has no other numeric-string handling yet. - `BranchService.assertOwned` was made `public` (was `private`) so Staff and Service can call it directly, per CONVENTIONS.md's "call the parent module's service to verify ownership" rule — same relationship Branch already has with `SalonService.assertOwned`.

### Module 5 — Availability
- Migration `0004_kind_mattie_franklin.sql` adds a **minimal** `bookings` table — only `branchId`, `selectedStaffId`, `scheduledStart`, `scheduledEnd`, `bookingStatus`, timestamps. This is deliberately not the full TRD `bookings` schema; Booking (Module 6, not started) will `ALTER TABLE` to add `customerId`, `salonId`, `bookingNumber`, `bookingType`, amounts, reasons, and approval/completion/cancellation timestamps when it builds real create/approve/cancel/reschedule flows. Never soft-deleted or hard-deleted, per TRD.
- `GET /api/v1/availability/slots`, `GET /api/v1/availability/staff` — both public, no auth. Query: `branchId`, `date` (YYYY-MM-DD, not in the past), `serviceIds` (**comma-separated** — not specified in frontend_handover.md, this is the chosen convention; e.g. `?serviceIds=id1,id2`).
- Three architectural gaps existed before this module could be built at all — resolved with the user, not guessed:
  1. **No slot-template CRUD exists** (`branch_slot_templates` was explicitly deferred in Module 3, no endpoint anywhere). Resolved: slots are generated at a **fixed 30-minute interval** (`DEFAULT_SLOT_INTERVAL_MINUTES` in `shared/constants.ts`) across the branch's `openingTime`→`closingTime`, ignoring `branch_slot_templates` entirely. Revisit if/when a template contract is ever added.
  2. **Capacity validation needs live bookings, but Booking (Module 6) doesn't exist.** Resolved: the minimal `bookings` table above. Right now it's always empty (nothing can insert into it until Module 6 ships), so capacity is effectively governed by chairs/staff only — but the overlap-counting logic is real and already correct for when rows start appearing.
  3. **Redis caching skipped.** TRD lists a `cache:availability:{...}` key but explicitly leaves its TTL "not numerically finalized" — decided to compute live on every request for MVP rather than wire invalidation across 5 mutation points (staff/leave/holiday/capacity-rule/service) for an unfinalized optimization. Add later as a hardening pass if needed.
- Capacity formula implemented exactly per TRD: `MIN(branch.totalChairs, activeServiceStaffCount, capacityOverride)`, where `activeServiceStaffCount` excludes staff with an `APPROVED` leave overlapping the specific candidate slot window (not just the whole day). Overlap check for both staff leave and existing bookings uses the TRD's exact `existing.start < new.end AND existing.end > new.start` rule (`end == start` is correctly treated as non-overlapping).
- `GET /availability/staff` is a **day-level** listing (frontend_handover.md's contract has no time param, only `date`): it excludes a staff member only if their `APPROVED` leave fully covers the entire business-hours window for that date. A staff member on leave for only part of the day still appears — the precise per-slot conflict is re-checked by `GET /availability/slots` and again inside the future booking-creation transaction (Module 6).
- `slotId` in the response is a plain `"HH:MM-HH:MM"` string (e.g. `"10:00-11:30"`) — not a persisted row, per TRD ("slot IDs are UI helpers"). Module 6's `POST /bookings` will need to decode this same format when it accepts a `slotId`.
- Response shape is a **bare array** for both endpoints (no `{success,data}` envelope), matching frontend_handover.md's literal documented shape — same exception category as `GET /users/me`.
- Verified end-to-end manually against a temporary local instance (real salon/branch/service/staff via the actual API, salon verification flipped directly in Postgres since no Admin endpoint exists yet) before this entry was written: confirmed capacity math, staff-leave capacity reduction, holiday short-circuit (`[]`), invalid-service 400, and the overlap boundary edge case, then cleaned up all test rows. Postman collection/spec ("Salonjaa API") has **not** been updated yet for this module — still only covers Modules 1-4.

### Module 6 — Booking
- Migration `0005_boring_timeslip.sql` ALTERs the minimal `bookings` table from Module 5 up to (most of) the TRD's full schema, and adds `booking_services`, `booking_status_history`, `booking_reschedule_requests`. Two intentional deviations from the TRD's exact column list, both decided with the user:
  - `bookings.customerName`/`bookings.customerPhone` (nullable) — TRD's bookings table has no columns for an unregistered walk-in customer's identity, but `POST /salon-bookings/walk-in`'s documented body requires them. `customerId` stays null for walk-ins rather than fabricating a synthetic `users` row.
  - `booking_reschedule_requests.responseReason` (nullable) — TRD lists a single `reason` column, but `POST /bookings/:id/reject-reschedule`'s documented body needs its own reason distinct from the original requester's.
- `POST /api/v1/bookings` (Customer) — creates a PENDING booking, snapshots each service's name/duration/price into `booking_services` (immutable), reserves capacity immediately. Bare `{ bookingId, status }` response, no envelope, per frontend_handover.md.
- `GET /api/v1/bookings/:id` (customer owner, owning Salon Owner, or ADMIN role) — bare `{ booking: {...} }`, per frontend_handover.md. `GET /api/v1/bookings/my-bookings` (Customer) — default envelope, optional `status` filter.
- `POST /api/v1/bookings/:id/cancel` (Customer owner) — **provisional policy, explicitly flagged**: any PENDING/APPROVED booking cancellable any time before scheduled_start, no cutoff, no strike ever recorded. The client's actual cancellation/strike policy is still unresolved (context.md Pending Decisions); user explicitly asked to ship this safe placeholder now and update later.
- `POST /api/v1/bookings/:id/reschedule-request`, `/approve-reschedule`, `/reject-reschedule` — customer proposes a new time, owning Salon Owner decides. No `requestId` in these routes (matches the documented paths exactly), so approve/reject always resolve the booking's latest PENDING `booking_reschedule_requests` row. Full capacity/staff recheck happens at approve time; only a light branch-hours/holiday check happens at request time.
- `GET /api/v1/salon-bookings`, `/approve`, `/reject`, `/propose-reschedule`, `/walk-in` (owning Salon Owner) — `propose-reschedule` creates a `SALON`-initiated reschedule request, but **no documented endpoint exists yet for the customer to accept/reject it** (context.md Pending Decisions flags this exact gap) — the request sits PENDING until such an endpoint is added. `walk-in` requires `staffId` (derives branchId/salonId from the staff record — decided with the user, since the documented walk-in body has no branchId/salonId field at all) and creates the booking straight to `APPROVED` (no customer-facing approval flow needed for walk-ins, per TRD). `POST /salon-bookings/:id/block-slot` is explicitly "Future Feature — Not MVP" per the docs — not implemented.
- **Not built**: booking check-in OTP (`booking_otps` table, one-time check-in code) — no endpoint for this exists anywhere in frontend_handover.md, so per scope discipline it's skipped entirely, not just deferred. Revisit only if a contract is added. The "approve then 15-minute payment window" business rule the client described is also not enforced here — `BookingStatus` has no intermediate "awaiting payment" state, and there's no Payment module yet to actually check payment status against; decided with the user that Payment module will own this rule when it's built (creating the order on approval and enforcing its own timeout), rather than Booking carrying a rule it can't act on.
- Concurrency: `POST /bookings` and walk-in creation run inside one Postgres transaction serialized per-branch via `pg_advisory_xact_lock(hashtext(branchId))` — no Redis lock involved (decided with the user; matches "Redis is never the booking source of truth"). Verified manually: two concurrent-ish overlapping bookings for different staff both succeed up to capacity, a third correctly gets `409`, and requesting the same staff member twice for an overlapping window correctly gets its own `409` ("staff no longer available") independent of the branch-capacity check.
- Booking expiry: BullMQ job (`booking.expire` queue) scheduled on every PENDING booking creation, delay = `BOOKING_DEFAULT_EXPIRY_HOURS` (env, default 12). Worker re-checks the booking is still PENDING before acting (safe no-op otherwise) rather than tracking/cancelling stale jobs — verified both paths manually (a still-PENDING booking flips to EXPIRED with a status-history row; an already-CANCELLED booking is untouched).
- **Bug found and fixed along the way**: `src/config/queue.ts`'s pre-existing `QUEUE_NAMES` (from earlier scaffolding, not written in this module) used `:` as a separator (e.g. `"booking:expire"`) — BullMQ v5 rejects any queue name containing `:` and throws at construction time. Renamed all of them to use `.` instead. This crashed the locally-running dev server via `tsx watch`'s auto-reload the moment `booking-expiry.queue.ts` was added, before the fix landed — server was restarted afterward and confirmed clean.
- Verified end-to-end manually against a temporary local instance (real salon/branch/2 staff/service, salon verification flipped directly in Postgres): full create→approve/reject→cancel→reschedule-request→approve-reschedule flow, walk-in, capacity exhaustion (2 chairs/2 staff → 3rd overlapping booking rejected), staff-specific conflict, holiday blocking, operating-hours validation, salonId/branchId mismatch validation, role-based 403s, and the expiry worker (both the real transition and the safe no-op) — all confirmed correct, then all test rows cleaned up. Postman collection/spec still not updated (unchanged since Module 4, per the user's earlier explicit "no need" — see the /postman:sync note in git history).

### Module 7 — Payment + Coupon
- Migration `0006_chunky_pixie.sql` adds `payments`, `payment_transactions`, `refunds`, `refund_history`, `coupons`, `coupon_usages`, `booking_coupons`, `settlements`, `settlement_bookings` per TRD §4, unchanged from the TRD's column lists.
- Provider: Razorpay (resolves context.md's previously-pending "exact payment-provider selection"). `RAZORPAY_KEY_ID`/`RAZORPAY_KEY_SECRET` in `.env` — app boots fine without them (same pattern as SMTP); `POST /payments/create-order` and `POST /payments/verify` throw a clear `InternalServerError` at request time if unset, not a boot-time crash. `PaymentProvider` interface + `RazorpayProvider` implementation in `src/providers/payment/`, matching the existing OTP/Email provider-adapter pattern.
- **Scope decision**: only the two documented client-driven endpoints are built (`create-order` → Razorpay checkout on the frontend → `verify` with the returned `orderId`/`paymentId`/`signature`). No webhook receiver endpoint exists anywhere in frontend_handover.md, so none was built — payment status only updates when the client actually calls `/verify`. Signature verification is manual HMAC-SHA256 (`orderId|paymentId`, key_secret) via `crypto.timingSafeEqual`, matching Razorpay's documented client-side verification scheme.
- `POST /payments/create-order` (Customer) requires the booking to be `APPROVED` first — decided with the user ("if salon owner approves then customer will pay") — and blocks a second order while one is `PENDING`/`SUCCESS` (a `FAILED` order can be retried). Literal bare `{ orderId, amount, currency }` response. `POST /payments/verify` is idempotent (re-verifying an already-`SUCCESS` payment just returns success again) and literal bare `{ success, paymentStatus }`.
- `GET /payments/:paymentId` (payment's own customer, owning Salon Owner via the booking's salonId, or ADMIN), `GET /payments/my-payments` (Customer) — default envelope.
- `POST /payments/refund-request` (Customer) — **provisional policy, explicitly flagged**, same treatment and same underlying pending-decision entry as booking cancellation: booking must be `CANCELLED` or `COMPLETED` with a `SUCCESS` payment, full amount only, one refund per payment, no time-window/percentage rule since none is defined. User explicitly asked to ship this now and add the real policy later (alongside the cancellation policy).
- `GET /payments/refunds` (Customer), `GET /payments/salon-settlements` (owning Salon Owner) — default envelope; settlements is a pure read against whatever rows exist (TRD: "manual MVP records", nothing creates them yet — same precedent as salon verification being flipped manually in Postgres).
- `POST /payments/coupons/validate` — pure preview check, **no side effects**: no documented endpoint anywhere attaches a coupon to a booking (`POST /bookings`'s body has no `couponCode` field), so `usedCount`/`coupon_usages`/`booking_coupons` are never written. Literal bare `{ valid, discount }` on success; invalid/expired/exhausted/below-minimum coupons throw `422` (matches the endpoint's documented error codes) rather than a soft `{valid:false}`.
- Coupons have no CRUD endpoint anywhere (same situation as `service_categories` in Module 4) — `npm run db:seed` now also seeds 2 starter coupons (`WELCOME10` 10%/max ₹150/min ₹200, `FLAT50` fixed ₹50/min ₹300), decided with the user, same precedent as category seeding.
- **Not enforced**: the client's described "approve then 15-minute payment window" — no `AWAITING_PAYMENT` state exists in `BookingStatus`, and there's no reliable way to check payment completion without a webhook. Decided with the user in Module 6 that Payment module would own this rule; still not implemented — would need either a webhook (undocumented, skipped per scope discipline) or client-side polling, neither of which is currently in the contract.
- Verified end-to-end against a temporary local instance, including **real Razorpay test-mode API calls** (not mocked) once the user supplied real test keys: create-order gating (rejects a PENDING booking, succeeds once APPROVED, blocks a duplicate while PENDING/SUCCESS, allows retry after FAILED), signature verification both ways (a fabricated signature correctly fails and marks the payment FAILED; a correctly-computed HMAC using the real key_secret correctly succeeds and is idempotent on re-verify), refund-request gating (blocked before cancellation, blocked without a SUCCESS payment, blocked on duplicate), ownership checks on payment detail, empty settlements read, and coupon math (percentage, fixed, max-discount cap, below-minimum 422, unknown-code 422) — all confirmed correct, then all test rows cleaned up (seeded coupons left in place).

### Module 8 — Review + Notification
- **Notification**: `NotificationChannelProvider` interface in `src/providers/notification/`, matching the existing OTP/Email/Payment adapter pattern the user asked to keep. `EmailChannelProvider` (the only implementation) wraps the existing `EmailProvider`. Adding SMS/WhatsApp later is a one-line registration in `src/providers/notification/index.ts` — the dispatch worker already looks providers up generically by `notifications.type` and treats a missing entry as "not deliverable yet," not a crash. No new endpoints — `frontend_handover.md` has no Notification section at all; this is a purely internal delivery mechanism, matching TRD §11's description of it as event-triggered email, not a queryable resource.
- Delivery is async via BullMQ (`notification.send` queue, TRD §10): `NotificationService.notify()` persists a `notifications` row then enqueues delivery — it never throws, so a notification failure can never break the caller's primary action (booking approval, cancellation, etc.), same defensive philosophy as `AuthService.sendOtp`'s existing try/catch. Worker retries 3x with exponential backoff, marks `FAILED` only after the final attempt.
- Templates are hardcoded per event type (`notification.templates.ts`), not read from the `notification_templates` table — matches the existing precedent (`EmailOtpProvider` already hardcodes its OTP subject/body; the table has stayed schema-only/no-consumer since Module 1).
- Wired into Booking (created/approved/rejected/expired/completed/cancelled/all 3 reschedule directions) and Payment (refund requested) at the exact TRD §11 event list, minus OTP (already has its own path) and promotions (module not built). Notifications route to whichever party makes sense per event (customer for their own booking's status changes, the salon owner for customer-initiated actions like cancellation/reschedule-request) — added `SalonService.findOwnerUserId(salonId)` for the latter. Walk-in bookings are skipped (no `customerId`, nothing to notify).
- **Real gap resolved with the user**: Reviews require a `COMPLETED` booking, but no documented endpoint anywhere transitions a booking to that status. Added a new BullMQ job (`booking.complete`, not in the TRD's original list) that auto-transitions an `APPROVED` booking to `COMPLETED` when `scheduledEnd` passes — same delayed-job mechanism as booking expiry. Rescheduling a booking correctly re-times (not duplicates) this job via a deterministic `jobId` (`rescheduleBookingCompletion`), so an approved reschedule doesn't leave a stale job that would complete the booking at the *old* time.
- **Review**: `POST /reviews`, `PATCH /reviews/:reviewId`, `GET /reviews/:reviewId` (public), `GET /reviews/salon/:salonId` / `.../service/:serviceId` / `.../staff/:staffId` (public), `POST /reviews/:reviewId/report`, `POST /reviews/:reviewId/reply` (owning Salon Owner). `reviews` has no direct `serviceId` column (matches TRD §4 exactly) — the service-scoped listing is a join through `bookings` → `booking_services`. Category ratings (`serviceRating`/`staffRating`/`hygieneRating`/`ambienceRating`/`productRating`) live in `review_category_ratings` as generic `(category, rating)` rows per TRD's schema; added a `review_category` enum (`SERVICE`/`STAFF`/`HYGIENE`/`AMBIENCE`/`PRODUCT`) since the TRD's enum list (§6) doesn't define one but the documented request body needs concrete values.
- **Not built**: `POST /reviews/:reviewId/images` — frontend_handover.md says "image upload contract not supplied," genuinely no format to build against. Decided with the user to skip entirely rather than guess (no multipart/base64/URL assumption baked in); the `review_images` table itself also wasn't created, consistent with not building schema ahead of a real consumer.
- **Provisional, same treatment as booking cancellation/refund**: the review edit period ("allowed edit period" per frontend_handover.md) is one of context.md's Pending Decisions — no cutoff is enforced; `PATCH /reviews/:reviewId` works at any time and just sets `isEdited = true`.
- Verified end-to-end against a temporary local instance, **with real SMTP delivery** (Mailtrap sandbox, already configured in `.env`) — not mocked: booking creation → notification persisted → BullMQ job → actual email sent → `notifications.status` flips `PENDING → SENT`, confirmed for `BOOKING_CREATED`, `BOOKING_APPROVED`, and `BOOKING_COMPLETED`. Forced the auto-completion job to a short delay to confirm the real transition (`APPROVED → COMPLETED`, `completedAt` set) rather than just reading the code. Then confirmed the full Review flow: create on a genuinely-completed booking, blocked on a still-`PENDING` one (409), duplicate-review rejection, rating-bounds validation (400), edit setting `isEdited`, public unauthenticated reads (detail + all three listing endpoints, including the service-join listing), owner reply embedding correctly in the review DTO, report + duplicate-report rejection (409), and the reply-requires-`SALON_OWNER` role check (403 for a customer). All test rows cleaned up afterward.
